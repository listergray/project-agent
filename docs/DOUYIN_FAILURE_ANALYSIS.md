## 原实现的原因与证据边界（修复前）

1. **主要阻塞点是本地封面验收与页面最终状态不一致。** `app/publisher.py` 的 `_set_covers` 完成选图和点击“完成”后，主要等待编辑弹窗关闭；`_verify_covers_with_llm` 只采集一次页面事实，没有等待横竖预览稳定、没有失败后复核。随后失败门禁在最终“发布”之前直接退出。两张失败截图证明，退出时页面已显示双封面，不能把通用报错直接解释为素材未上传或抖音拒绝发布。
2. **具体是定位错误、预览异步更新，还是两者并存，尚需发布前的实时 DOM 证据。** `_cover_slot_roots` 按文字及相邻/祖先节点寻找容器；`_node_has_cover_image` 依赖图片尺寸、canvas 或后代内联背景样式。现有截图不能说明每个检测分支实际匹配了哪个节点。截图比封面事实采集晚约 10–16 秒，因此也不能排除检查过早。不要把某个具体选择器失效写成已经复现的结论。
3. **DeepSeek 没有独立检查图片。** `app/llm_judge.py` 发送的是 `cover_v_ok`、`cover_h_ok` 等文本事实，没有发送截图；`_verify_covers_with_llm` 在 DOM 不通过时强制判失败。仅关闭模型检查无法消除 DOM 检测造成的拦截。提示词本身还有连续问号形式的损坏文本，应在后续修复中处理，但不是这些日志中封面失败的独立证据。
4. **浏览器资源没有真正排队。** `publish_video` 最多等锁 5 秒；保活也占用同一把锁，并需访问两个页面。`main.py` 启动独立线程并把 `ok=False` 统一写为 `FAILED`，导致短暂忙碌也显示成发布失败。页面绿色登录状态与浏览器能否立刻用于发布是两个不同状态。
5. **另有非本次主阻塞问题。** 两轮日志均有简介话题输入的定位超时，但失败截图已经显示 `#ai编程` 和 `#干货`，最终错误也未包含话题缺失，说明不能把这条警告当成此次终止的原因。定位填写函数没有成功状态反馈，主流程也没有读回校验，失败截图中位置输入仍为空，后续应单独验证。

## 原建议与实施范围

1. **已实施**：点击封面“完成”后，默认最多等 60 秒，横竖预览连续两次稳定才确认；保存每轮检测事实及匹配节点摘要。
2. **已实施**：按可见横竖标签限定预览区域，支持已加载图片、CSS 背景及非空画布；处理隐藏重复标签、预览与标签分行布局、明确缺失提示，排除坏图、纯背景色、空画布和普通方形图标。
3. **已实施**：封面放行由页面实测决定，不再调用文字模型判断图片；仍要求选图/保存流程成功，避免默认预览掩盖实际选图失败。原 `llm_judge.py` 保留但已退出此封面检查流程，其损坏提示词未在本次修复。
4. **已实施**：发布按 FIFO 排队，默认最多等浏览器 900 秒；后台保活在有发布等待时让位；取消或超时的等待者会移出队列。等待仍使用 `RUNNING` 状态，进度消息明确显示排队；同一集的活跃任务复用，避免重复点击创建多个发布。
5. **部分实施**：封面失败结果区分选图/保存未完成与预览未确认，附检测记录和截图；浏览器等待超时带 `stage=browser_wait`。简介与定位输入的额外修正、读回验收留待后续，不能据此宣布定位已经正常。
6. **验证边界**：已完成 17 项离线回归，覆盖真实 Chromium 中的模拟封面表单、延迟与短暂预览、失败时禁止调用发布、正常表单放行、保活超过 5 秒、排队优先级/取消/超时和任务去重。真实抖音页面的 DOM、定位及最终发布仍待后续实际操作验证。
